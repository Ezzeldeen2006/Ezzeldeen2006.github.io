Backend

Money Transfer API

Spring Boot money transfer service built during my Aman Holding internship: atomic transfers under optimistic locking, JWT sessions whose invalidation actually sticks, and 87 integration tests over all 15 endpoints.

  • Java
  • PostgreSQL
  • REST API
  • Spring Boot
  • Spring Security
  • Testing

Systems implemented

  • Atomic transfers. The debit, the credit and the ledger entry commit as one @Transactional unit, with @Version optimistic locking on the account row. Two concurrent transfers out of the same account cannot both spend the same balance — the loser gets a 409 instead of a silent overdraft. Three flows share that one path: between my own accounts, to another user, and out to an external bank.
  • A ledger that does not rewrite history. Each transaction stores a snapshot of the recipient's account number and name rather than only a foreign key. History stays correct after an account is renamed or closed, and an external recipient needs no account row at all — which is what made external transfers possible to insert in the first place.
  • Verification before money moves. One call confirms the recipient exists, returns the holder's name masked to initials so a sender can recognise it without learning a stranger's full name, and reports whether the sender can cover the amount. Ownership is enforced on the source account, so the check cannot be turned into a way of reading someone else's balance.
  • Identity from the token, never from the request. No endpoint accepts a user id. The caller is whoever the JWT says they are, so there is no parameter to tamper with — the safest way to validate an id is not to take one.
  • Session invalidation that sticks. The 30-minute inactivity rule rejected exactly one request and then accepted the identical retry, because timing a token out deleted the only record that it had timed out. Invalidation is now recorded with a reason and cannot be undone, keyed by a SHA-256 digest instead of the raw token, and swept when the token's own expiry passes.
  • Paginated, date-filtered history without the N+1. A page of twenty rows was firing forty extra selects to name each party. Fetch-joining the accounts and their users removed them, and because every relation is many-to-one the database still applies LIMIT and OFFSET itself.
  • Tests at two levels. 87 JUnit tests drive the real security filter chain through MockMvc — including rollback on insufficient funds and isolation between two users — and a 72-request Postman/Newman suite ends by re-reading every balance to prove the rejected transfers rolled back rather than half-committing.

Fifteen endpoints across registration and login, profiles, accounts and sub-accounts, transfers, history and saved recipients, with a small React client to drive them. Java 25, Spring Boot 4, Spring Security 6, Spring Data JPA and PostgreSQL 18, documented with Swagger/OpenAPI.

Built in summer 2026 during my backend internship on the Bill Payment team at Aman Holding, against the company's written specification for a money transfer service. It is a training project rather than a production system, and the repository is private, so there is no link to it here.
